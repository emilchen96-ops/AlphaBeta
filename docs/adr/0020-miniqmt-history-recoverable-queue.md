# ADR 0020：MiniQMT 历史补数采用可恢复确认、持久去重与死信隔离

- 状态：Accepted
- 日期：2026-08-04

## 背景

SC02-D 智能选股和 BT02/BT03 分钟触发回测会通过 Redis 请求 Windows MiniQMT 只读 Agent
补齐历史行情。旧实现入队时只做短时去重，领取任务时立即删除，并把自动维护、实时快照与历史
下载放在同一错误边界中。慢速全市场任务会在去重过期后重复入队；Agent 在自动维护上传超时或
实时报价返回 4xx 时无法推进历史队列；领取后崩溃还会永久丢失任务。页面因此可能长期显示
大量股票“正在下载”，但实际队列没有进展。

## 决策

1. 历史请求使用证券集合、周期、复权和时间范围生成稳定指纹。去重标记持续到任务完成或进入
   死信，不再依赖短 TTL。
2. Agent 只查看队首任务，不在领取时删除。全部数据经 API 幂等写入 PostgreSQL 后显式确认并
   删除；进程或网络故障时任务自然保留。
3. 失败任务累计次数并轮转至队尾，使其他任务继续；连续失败 3 次后写入死信列表并释放指纹，
   允许修复后重新提交。
4. Agent 启动时压缩旧版重复和损坏项，并补建活动指纹。支持的 Worker 和 API 必须统一使用
   入队服务，不得直接 `RPUSH` 绕过去重。
5. 历史补数优先于自动维护。自动维护、回调快照或单个 4xx 数据错误必须被隔离，不得使 Agent
   重连循环饿死历史队列。
6. 每次确认或重试后按 `scan_run_id` 或批量回测共享的 `correlation_id` 轮转队列。不同选股、
   回测任务交替获得处理机会，单个全市场任务不得让其他任务长期停留在 0%。旧版只带独立
   `backtest_run_id` 的批量请求按来源归组，避免把同一批次的每只股票误判成独立工作流。
7. PostgreSQL K 线唯一键继续作为最终幂等边界；Redis 只协调工作，不成为行情事实来源。
8. API 进程重启或本地连接短暂中断时，Windows Agent 原地重建 HTTP 客户端并持续退避重试，
   保持 MiniQMT 会话与当前未确认任务不变。
9. XtQuant 同步历史下载设置可中止超时。超时请求主动停止、轮转重试并最终进入死信隔离，
   不允许一个外部调用无限占据队头。

## 结果

- 重复点击、Worker 重启、Agent 重启和 API 短暂故障不会反复制造等价积压或静默丢失任务。
- 单个坏任务不会永久阻塞队首，失败原因可从死信记录审计并重试。
- 大批量回测与全市场选股并存时会公平推进，不要求前一个任务全部完成后才开始下一个任务。
- 仍然只有一个受支持的 Windows Agent 消费历史队列；该决策不引入交易 SDK、账户读取或下单。
- Redis 完全丢失时仍需依据 PostgreSQL 覆盖度重新规划缺口，但已持久化行情无需重复保存。

## 否决方案

- **领取即删除**：实现简单，但进程崩溃会丢失任务。
- **仅延长去重 TTL**：无法覆盖未知时长的全市场队列，也不能解决成功前任务丢失。
- **失败时持续重试队首**：一个异常证券即可饿死全部后续任务。
- **直接清空积压**：只能暂时改善页面，无法阻止同一故障再次发生。
